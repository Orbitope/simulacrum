Simulacrum · vectorizing RL environments

Make your environment 100× faster. Keep the one you can read.

A readable Python environment steps about 385,000 times a second. The same environment written as batched tensors steps 35 million times a second. It is also a different program, which is why most people never trust it enough to throw the readable one away. This is how you keep both and prove they are the same environment. Everything on this page is running live in your browser.

Why bother

The environment is usually the bottleneck.

In most RL training loops the policy update is not what is slow. Collecting experience is. A simulator written the readable way steps one instance at a time through the Python interpreter, and no amount of GPU will help, because the GPU is idle waiting for samples.

Rewriting the simulator so every instance advances in one tensor operation removes that ceiling. Here is what it is actually worth, measured on the two example environments in this repository:

Two things in that chart are worth pausing on. The first is the scale: ninety-two times the throughput of the readable implementation, and it is still climbing at N = 8192.

The second is more useful. At N = 1 the batched version is slower than the readable one: 13,567 steps/s against 385,199. Vectorization is not a free win you sprinkle on; it is a trade that only pays above a few hundred instances. If you are running one environment at a time, the readable implementation is the fast one.

The catch

The fast version isn't an optimization. It's a second program.

The readable version has one agent and an if. The fast version has ten thousand agents and no branches at all, because you cannot branch per-instance across a batch. Every if becomes arithmetic that computes both outcomes and discards one.

This is where most attempts stall, and the reason is not difficulty. It is trust. Once the two programs exist, nothing checks that they are the same environment, and a subtly wrong simulator still produces a training curve that goes down. So you end up choosing: keep the version you can reason about and train slowly, or take the speed and stop being able to explain your results.

That choice is avoidable. The rest of this page is how.

The proposal

Don't replace the readable one. Keep both, and hold them to the same spec.

Write the environment twice. Once so a person can read it: explicit ifs, one instance, every line traceable. Once so a batch of ten thousand can run it. Both are written from a single spec.md, and never from each other.

Then have a machine check, step by step, that they produce bit-identical states, rewards, terminations and observations. If they agree, either you implemented the spec correctly twice, or you made the same misreading twice in two very different programming styles. The second is a far weaker coincidence than getting it right once by luck.

What that buys you is specific: the readable implementation stays the thing you reason about, debug against and explain your results with, and the fast one is provably the same environment. You are not trading interpretability for throughput. You are keeping the first and adding the second.

Three things have to work for that to be true, and the rest of this page is those three, each running live.

What you're actually installing

Simulacrum is the part you'd otherwise write yourself.

None of the above is a technique you hand-roll per project. It's a Python package: pip install, then simulacrum new myenv lays down the skeleton. You fill in four files. Everything that makes the comparison possible is already there.

What the package supplies underneath is the awkward machinery you would otherwise get subtly wrong: the counter-based RNG in both a scalar and a tensor flavour, guaranteed bit-identical; a BatchedEnv base class that owns the step loop, in-tensor auto-reset, terminal-state capture and invariant checking; trajectory read/write against your schema; and the report gate. Your fast.py for forager is about sixty lines, because the base class does everything that isn't the game itself.

Two commands and one import. The rest of this page is what they buy you.

Requirement one

Two programs can't agree unless they roll the same dice.

Here is the problem that sinks most attempts before they start. The readable version draws randomness one instance at a time. The batched version draws for ten thousand at once and discards most of them. With an ordinary random generator, one that carries a stream position, those discarded draws advance the state, and the two programs desynchronise permanently on the first step.

Simulacrum removes the stream entirely. Every random decision is a pure function of four numbers:

bits = hash(episode_key, step, slot, index)

No history, no cursor, nothing to keep in sync. A slot names which decision this is; index separates repeats of the same decision, one per berry, say. Move the sliders: the draw depends on those four numbers and nothing else.

Nothing moved. That is the entire trick, and three hard problems fall out of it at once: the batched code can draw for all ten thousand instances and mask, because a discarded draw was never part of a sequence; an episode that ends early can re-key and restart in place without telling anyone; and a port to another array framework is mechanical, because there is no hidden state to port.

That last point is not hypothetical. The environment you are about to play with is running from a 90-line JavaScript port of exactly this generator.

The environment

Meet forager. It's small on purpose.

An 8×8 grid. Six berries, three kinds worth 0.10, 0.15 and 0.30 energy. You start with 1.0 energy and lose 0.02 a step, so you have fifty steps unless you eat. Each step you pick a compass direction, and 15% of the time a gust rotates your move 90° clockwise. That gust is the stochasticity that makes agreeing on randomness hard.

Requirement two

The guarantee, and what it feels like when it fires.

Two copies run side by side on the same seed and the same actions: the readable one on the left, the batched one on the right. One bug is switched on already, so you land on a real divergence. Untick it to watch 300 steps come back identical, then try the others.

These are not invented mistakes. Every one is a real way a readable environment gets mistranslated into tensors, and each carries a cost line: what your agent actually learns instead. That is the part worth reading. Most of these leave a perfectly trainable environment behind, so without the check none of them would ever announce themselves. You would just get a slightly different game and a plausible learning curve.

Requirement three

A guarantee that survives scale.

Everything so far compares the batched implementation against the readable one, and the readable one only knows how to be a single instance. So that comparison runs at N = 1, and the whole reason you are vectorizing is to run at N = 8192. There is a real hole there, and here is what falls through it.

Somewhere in the batched code, a mask of shape [N] meets a quantity of shape [N, 1]. In NumPy and PyTorch that is not an error. It is a broadcast, and it silently produces an [N, N] matrix. A reduction downstream collapses it back to a perfectly plausible [N]. One character of difference:

With one instance, that accidental matrix is 1×1, which is exactly the right answer. The bug is not merely missed; it is mathematically invisible at the only batch size a reference comparison can ever run at. And it appears precisely when you scale up, which is to say precisely when you started caring.

Making it stick

A guarantee you have to remember to check isn't one.

Ten tests run as a gate, not a habit. They write a report; training scripts read it and refuse to start if it is missing, failing, or older than the environment's source files. Edit fast.py and go straight back to training and you get stopped, because the report no longer describes the code you are about to run.

This is the real output of simulacrum validate examples/forager, the environment you have been playing with above.

Evidence, not proof. Two implementations agreeing means the same misreading would have had to happen twice, in two very different styles. That is a weak coincidence, not a formal verification.
The page's JavaScript shares an author with the Python. It is a third implementation from the same spec, checked bit-for-bit across 1,500 steps, not an independent audit. What it shows is that the spec is precise enough to rebuild from.
What it costs

You write the environment twice. That's the bill.

It is a real cost and worth stating plainly: a second implementation, and the discipline to write it from the spec rather than from the first one. In exchange the readable implementation stops being a liability you eventually delete, and becomes the thing that certifies the fast one on every run.

Starting from an environment you already have is the easy direction. Your existing readable implementation is the reference. Write down its spec, add the batched one, and let the battery tell you where the two disagree. Every divergence it reports is a place your spec was ambiguous, which is worth knowing regardless.

Keep the one you can read.

Vectorizing your simulator should not mean giving up the ability to explain what it does. Write it once for people, once for the hardware, and let a machine hold both to the same spec, so the speed comes with a receipt.
