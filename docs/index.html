Simulacrum · differential-testing RL environments

Your fast environment is lying to you.

To train an agent at any scale you rewrite your simulator as batched tensor code — a hundred times faster, and a completely different program. If the rewrite is subtly wrong, the loss curve still goes down. You get an agent that is excellent at a game you never meant to build. Every environment on this page is running live in your browser.

The problem

A batched environment isn't an optimization. It's a second program.

The readable version has one agent and an if. The fast version has ten thousand agents and no branches at all — because on a GPU you cannot branch per-instance, so every if becomes arithmetic that computes both outcomes and throws one away.

These two are supposed to be the same environment. Nothing checks that they are.

The keystone

Two programs can't agree unless they roll the same dice.

Here is the problem that sinks most attempts before they start. The readable version draws randomness one instance at a time. The batched version draws for ten thousand at once and discards most of them. With an ordinary random generator — one that carries a stream position — those discarded draws advance the state, and the two programs desynchronise permanently on the first step.

Simulacrum removes the stream entirely. Every random decision is a pure function of four numbers:

bits = hash(episode_key, step, slot, index)

No history, no cursor, nothing to keep in sync. A slot names which decision this is; index separates repeats of the same decision — one per berry, say. Move the sliders: the draw depends on those four numbers and nothing else.

Nothing moved. That is the entire trick, and three hard problems fall out of it at once: the batched code can draw for all ten thousand instances and mask, because a discarded draw was never part of a sequence; an episode that ends early can re-key and restart in place without telling anyone; and a port to another array framework is mechanical, because there is no hidden state to port.

The environment

Meet forager. It's small on purpose.

An 8×8 grid. Six berries, three kinds worth 0.10, 0.15 and 0.30 energy. You start with 1.0 energy and lose 0.02 a step, so you have fifty steps unless you eat. Each step you pick a compass direction — and 15% of the time a gust rotates your move 90° clockwise. That gust is the stochasticity that makes agreeing on randomness hard.

The test

Now break it on purpose.

Two copies run side by side on the same seed and the same actions: the readable one on the left, the batched one on the right. Switch on a bug and watch them come apart — the agents separate, the berry sets drift, and the runner reports the first step where they disagree and the exact field that did it.

These are not invented mistakes. Each one is a real way a scalar environment gets mistranslated into tensors, and every one of them leaves a perfectly trainable environment behind.

The blind spot

And now the bug that test cannot see.

The differential test runs one instance against the reference, because the reference only knows how to be one instance. That is a real hole, and here is what falls through it.

Somewhere in the batched code, a mask of shape [N] meets a quantity of shape [N, 1]. In NumPy and PyTorch that is not an error — it is a broadcast, and it silently produces an [N, N] matrix. A reduction downstream collapses it back to a perfectly plausible [N]. One character of difference:

Now count the instances the differential test uses. One. And with one instance, that accidental matrix is 1×1 — which is exactly the right answer. The bug is not merely missed; it is mathematically invisible at the only batch size that test ever runs.

The point

None of this is worth anything as a suggestion.

Ten tests run as a gate, not a habit. They write a report; training scripts read it and refuse to start if it is missing, failing, or older than the environment's source files. An environment without a fresh passing report is not eligible for training.

This is the real output of simulacrum validate examples/forager — the environment you have been playing with above.

Two implementations are evidence, not proof. If both were written from the same spec and both agree, either the spec was implemented correctly twice or the same misreading happened twice in two very different programming styles. The second is possible. It is just much less likely than getting it wrong once — and it is not a claim of formal verification.
The speedup ratio is the least interesting number here. forager's reference implementation is itself fast — about 170,000 steps/s of plain Python — which deflates the ratio to 13×. The absolute figure, 2.3 million steps/s, is the one that matters, and it moved between 13× and 18× across runs on the same machine.
This page's JavaScript is a third implementation, not an independent audit. It was written from the same spec.md by the same author, so it does not carry the weight of a genuinely independent port. It is checked against the Python reference across 1,500 steps and five seeds — states, rewards, terminations and float32 observations all bit-identical — and the RNG is checked against 2,040 known-answer vectors. What that demonstrates is that the spec is precise enough to reimplement from, in a language with neither int64 nor tensors.
forager is a demo, not a benchmark. Eight by eight, six berries, one stochastic event. It exists to exercise vector state, per-item random draws and masked collection — the things a real environment needs and a scalar toy cannot show. It is not a claim about how the framework behaves on something large.

Write it twice. Prove they agree.

That is the whole idea, and the whole cost. You write the environment once so a human can read it, once so a GPU can run it, and let a machine hold them to the same spec — instead of finding out six weeks into a training run that your simulator had a favourite corner.
